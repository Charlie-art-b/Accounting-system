eficiencia y control de información financiera.

- Herramientas: Composer, NPM, Artisan, Vite, Git

ARQUITECTURA: MVC con Filament como capa de presentación

11 MÓDULOS CRUD:
1. Clientes | 2. Usuarios | 3. Proveedores | 4. Cuentas por Cobrar
5. Cuentas por Pagar | 6. Cuentas Contables | 7. Inventarios (por cliente)
8. Asientos Contables | 9. Activos Fijos | 10. Cobros | 11. Estados Financieros

2. MODELOS Y ESTRUCTURA DE BASE DE DATOS
================================================================================

TABLA: customers (Clientes)
- id, nombre, apellidos, tipo_identificacion (enum: cedula/pasaporte/juridica)
- identificacion (UNIQUE), correo (UNIQUE), telefono, direccion
- tipo_cliente (enum: persona_fisica/persona_juridica)
- estado (enum: activo/inactivo), observaciones, timestamps
Relaciones: hasMany CuentaPorCobrar, Cobro, Producto | belongsToMany Supplier

TABLA: users (Usuarios)
- id, nombre, apellidos, identificacion (UNIQUE), correo (UNIQUE)
- password (hashed), rol (enum: gerente/contador/auxiliar)
- estado (enum: activo/inactivo), email_verified_at, remember_token, timestamps
Roles: Gerente (acceso total), Contador (operativo), Auxiliar (solo consultas)
Relaciones: hasMany AsientoContable

TABLA: suppliers (Proveedores)
- id, tipo_proveedor (enum: persona/empresa), nombre_razon_social
- identificacion (UNIQUE), correo, telefono, estado, timestamps
Relaciones: belongsToMany Customer | hasMany CuentaPorPagar, Producto

TABLA PIVOT: customer_supplier
- id, customer_id (FK), supplier_id (FK), timestamps

TABLA: cuentas_por_cobrar
- id, customer_id (FK RESTRICT), numero_factura (UNIQUE)
- fecha_emision, fecha_vencimiento, descripcion
- monto_total (decimal 15,2), monto_pagado (decimal 15,2)
- saldo_pendiente (GENERATED: monto_total - monto_pagado)
- estado (enum: pendiente/parcial/cancelada/anulada), timestamps
Relaciones: belongsTo Customer | hasMany Cobro

TABLA: cuentas_por_pagar
- id, supplier_id (FK RESTRICT), numero_documento
- fecha_emision, condicion_pago (enum: contado/credito), plazo_pago
- fecha_vencimiento, tipo (enum: factura/recibo/nota_debito/otro)
- monto_total, monto_pagado, saldo_pendiente (GENERATED), fecha_pago
- estado (enum: pendiente/parcial/pagada/anulada), timestamps
Relaciones: belongsTo Supplier

TABLA: cuentas_contables
- id, codigo_cuenta (UNIQUE, ej: "1.1.01.001"), nombre_cuenta
- tipo_cuenta (enum: activo/pasivo/patrimonio/ingreso/gasto)
- estado (enum: activa/inactiva), nivel (calculado), cuenta_padre_id (FK), timestamps
Estructura jerárquica: 1 > 1.1 > 1.1.01 > 1.1.01.001
Relaciones: belongsTo CuentaContable (padre) | hasMany CuentaContable (hijas), DetalleAsiento

TABLA: productos (Inventario por Cliente)
- id, customer_id (FK RESTRICT), supplier_id (FK RESTRICT)
- nombre_producto, descripcion, categoria
- stock_inicial, stock_actual, timestamps
NOTA: Cada cliente tiene su propio inventario independiente
Relaciones: belongsTo Customer, Supplier | hasMany MovimientoInventario

TABLA: movimientos_inventario
- id, producto_id (FK CASCADE), tipo_movimiento (enum: entrada/salida)
- cantidad, motivo (enum: compra/venta/ajuste/devolucion)
- fecha_movimiento, observaciones, timestamps
Relaciones: belongsTo Producto

TABLA: asientos_contables
- id, numero_asiento (UNIQUE, autogenerado "AS-YYYY-NNNNNN")
- fecha_asiento, tipo_asiento (enum: ingreso/egreso/ajuste/general)
- descripcion, user_id (FK RESTRICT), periodo_contable (YYYY-MM)
- estado (enum: borrador/contabilizado/anulado), timestamps
Relaciones: belongsTo User | hasMany DetalleAsiento

TABLA: detalles_asiento
- id, asiento_contable_id (FK CASCADE), cuenta_contable_id (FK RESTRICT)
- descripcion_linea, debe (decimal 15,2), haber (decimal 15,2), orden, timestamps
CONSTRAINT: (debe > 0 AND haber = 0) OR (haber > 0 AND debe = 0)
Relaciones: belongsTo AsientoContable, CuentaContable

TABLA: activos_fijos
- id, nombre_activo, descripcion, valor_adquisicion, fecha_adquisicion
- vida_util_anos, valor_residual, depreciacion_acumulada
- valor_neto (GENERATED: valor_adquisicion - depreciacion_acumulada)
- estado (enum: activo/dado_de_baja), fecha_baja, motivo_baja, timestamps

TABLA: cobros
- id, cuenta_por_cobrar_id (FK RESTRICT), customer_id (FK RESTRICT)
- fecha_cobro, monto_cobrado, numero_comprobante
- metodo_pago (enum: efectivo/transferencia/cheque/tarjeta)
- observaciones, timestamps
Relaciones: belongsTo CuentaPorCobrar, Customer

================================================================================
3. REGLAS DE NEGOCIO CRÍTICAS
================================================================================

R1. BALANCE CONTABLE: SUM(debe) = SUM(haber) en asientos. NO guardar desbalanceados.

R2. ESTADOS AUTOMÁTICOS (Cuentas por Cobrar/Pagar):
    - monto_pagado = 0 → 'pendiente'
    - 0 < monto_pagado < monto_total → 'parcial'
    - monto_pagado = monto_total → 'cancelada'/'pagada'

R3. STOCK INVENTARIO (POR CLIENTE):
    - Cada cliente tiene su propio inventario independiente
    - entrada → stock_actual += cantidad
    - salida → stock_actual -= cantidad (validar cantidad <= stock_actual)
    - Los productos de un cliente no afectan el inventario de otros

R4. NO ELIMINAR CON DEPENDENCIAS:
    - Cliente con cuentas por cobrar o productos en inventario
    - Proveedor con cuentas por pagar
    - Cuenta contable con asientos
    - Producto con movimientos
    → Cambiar estado a 'inactivo' en su lugar

R5. RESTRICCIONES DE EDICIÓN:
    - No modificar cuentas 'cancelada'/'pagada'/'anulada'
    - No modificar asientos de períodos cerrados
    - No modificar código de cuenta contable si tiene asientos

R6. PERÍODOS CONTABLES (YYYY-MM):
    - Solo modificar/eliminar asientos del período actual
    - Períodos anteriores = cerrados

R7. PERMISOS POR ROL:
    - Gerente: Acceso completo
    - Contador: Módulos operativos (no gestión de usuarios)
    - Auxiliar: Solo consultas

R8. VALIDACIONES DE FECHAS:
    - fecha_vencimiento >= fecha_emision
    - fecha_asiento no puede ser futura

R9. TRANSACCIONES DB para:
    - Asiento contable (asiento + detalles)
    - Cobro (cobro + actualizar cuenta por cobrar)
    - Movimiento inventario (movimiento + actualizar stock)

R10. INTEGRIDAD REFERENCIAL:
     - ON DELETE RESTRICT: customer_id, supplier_id, cuenta_contable_id, user_id
     - ON DELETE CASCADE: asiento_contable_id, producto_id, customer_supplier

R11. NO usar soft deletes. Usar campo 'estado' (activo/inactivo).

EJEMPLO FILAMENT RESOURCE - Cliente (básico):

protected static ?string $model = Customer::class;

public static function form(Form $form): Form {
    return $form->schema([
        Forms\Components\TextInput::make('nombre')->required(),
        Forms\Components\TextInput::make('identificacion')
            ->unique(ignoreRecord: true)->required(),
        Forms\Components\Select::make('estado')
            ->options(['activo' => 'Activo', 'inactivo' => 'Inactivo']),
    ]);
}

public static function table(Table $table): Table {
    return $table->columns([
        Tables\Columns\TextColumn::make('nombre')->searchable(),
        Tables\Columns\BadgeColumn::make('estado'),
    ])->filters([
        Tables\Filters\SelectFilter::make('estado'),
    ]);
}

4. Al finalizar módulos, descomentar autenticación y crear Policies

Ver: app/Providers/Filament/AdminPanelProvider.php (líneas comentadas)

FILAMENT + POLICIES DE LARAVEL:
Filament respeta automáticamente las Policies de Laravel para controlar acceso
por roles. NO se definen rutas manualmente, todo se controla con Policies.

CREAR UNA POLICY POR CADA MODELO:
php artisan make:policy CustomerPolicy --model=Customer
php artisan make:policy UserPolicy --model=User
php artisan make:policy SupplierPolicy --model=Supplier
# Etc. para cada módulo

ESTRUCTURA ESTÁNDAR DE POLICY:

// app/Policies/CustomerPolicy.php
class CustomerPolicy
{
    // Controla si aparece en menú y puede ver lista
    public function viewAny(User $user): bool {
        return true; // Todos pueden ver
    }
    
    // Controla si puede ver detalles
    public function view(User $user, Customer $customer): bool {
        return true;
    }
    
    // Controla botón "New"
    public function create(User $user): bool {
        return in_array($user->rol, ['gerente', 'contador']);
    }
    
    // Controla botón "Edit"
    public function update(User $user, Customer $customer): bool {
        return in_array($user->rol, ['gerente', 'contador']);
    }
    
    // Controla botón "Delete"
    public function delete(User $user, Customer $customer): bool {
        return $user->rol === 'gerente'; // Solo gerente
    }
}

REGISTRAR POLICIES:

// app/Providers/AuthServiceProvider.php
protected $policies = [
    Customer::class => CustomerPolicy::class,
    User::class => UserPolicy::class,
    Supplier::class => SupplierPolicy::class,
    // ... todas las demás
];

AsientoContablePolicy - Validar período actual:
public function update(User $user, AsientoContable $asiento): bool {
    $periodoActual = now()->format('Y-m');
    return in_array($user->rol, ['gerente', 'contador']) 
        && $asiento->periodo_contable === $periodoActual;
}
